# 第四階段：施工前後照片建議配對與刪除復原

修改前版本：`62396865833c6193a73a5237cf412616d694e660`。開始時確認本機與GitHub `main`一致，沿用第一至第三階段的編輯器、同一時間軸、版本雜湊、ZIP快照及FFmpeg。沒有改動Gemini提示詞、模型、登入或渲染核心。

## 使用方式

1. 選「裝修前後對比」，在雙上傳區加入照片，或把來源照片的分類選為施工前／後；來源分類後會帶入新增配對選單。原「依順序自動配對」仍是明確由使用者操作的順序配對，與智慧建議分開。
2. 按「建議配對（不呼叫AI）」：顯示兩側縮圖、可換照片的選單、理由及中／低信心。沒有足夠資料時提示無法確定，仍可手動指定前後照片建立片段。
3. 接受才新增正式片段，拒絕不改內容。若與其他片段共用任一來源，需勾選「我確認保留既有配對，另加這組」；不覆蓋、不刪除、不改既有動畫。手動更換建議照片後，原建議理由不再適用，介面會明確提示。
4. 選取片段，在原設定區的「配對：施工前／施工後」直接更換任一來源，或按「交換施工前／後」。片段ID、播放位置、時長、動畫及既有文字保留；更換側的裁切採新來源設定，交換則交換兩張照片各自的裁切。AI文字標記待確認，不自動移動手動定位。
5. 要刪除來源，使用來源卡的「刪除來源」；一般照片用原本「刪除照片」。存在配對、封面參照或附屬文字時，先顯示實際影響及確認／取消；沒有關聯時直接刪除。獨立PNG不隨照片刪除，但超過新片長部分沿用既有截短規則。
6. 「復原最近刪除」一次還原來源、原順序、附屬文字、受影響配對、封面參照與被截短的PNG設定。復原前檢查內容是否仍符合刪除後版本，避免覆蓋之後的新編輯。
7. 不需要為本功能先按套用；正常下載ZIP／輸出MP4仍自動同步。第三階段相鄰輸出按鈕與快照流程不變。

「刪除對比片段」仍只移除片段、不刪照片；本階段單次復原針對來源照片刪除，不是全站Undo／Redo，也不包含檔案替換的回復。

## 配對實際依據

目前 `studio/ai.py` 的 `Analysis` 只有 `items`，項目欄位是 `label`、`description`、`category`、框／座標、`confidence_level`、`needs_review`。**沒有**獨立的空間類型、施工狀態或整張場景描述。本次不假設它們存在。

前端只讀已加入編輯器的 `source='gemini'` 標籤，使用其 `text`（由AI的label轉換）、`description`、`category`，以及既有照片 `role`、`name`：

- 從真實文字找明確空間詞：客廳、廚房、臥室、浴室、餐廳、陽台、玄關、書房等。文字同時含多種空間則視為不確定；明確不同空間不配對。
- 比較落地窗、橫梁、樓梯、中島、拱門等共同特徵。只有地板／照明等泛用裝修詞，不足以建議。
- 前／後以使用者來源分類為優先，沒有分類才讀檔名的施工前／後、before／after等明確字樣；不推測照片看起來新舊。
- 相同空間且有共同特徵，或有非泛用、相同的案例檔名識別，才提出候選；不以相鄰上傳順序判定。
- 僅「相同空間＋相同案例檔名＋共同特徵」標中信心；其餘標低。沒有高信心或百分比，因為沒有進行照片幾何／視角核對。AI項目的高信心不等於兩張照片是同一空間。
- 同空間多角度保留多個候選，不強制一對一，最多顯示12個建議。排序固定，不受上傳相鄰關係影響。

只在按建議按鈕時運算。來源、分析文字或既有配對改變後，舊建議提示重新產生；選取照片不重算。建議與拒絕記錄只在目前元件記憶體，元件重建可能清除，拒絕不是永久封鎖。沒有額外Gemini呼叫、影像比對、圖片重新編碼或付費服務。

## 正式配對與分類相容性

原本前後角色被當成配對有效性的硬條件：改分類會直接刪片段，交換前後也會驗證失敗。本次保留原片段結構，只調整有效性：兩個來源ID存在且不同即可，角色作為來源分類及建議依據，**片段的before_id／after_id才決定輸出前後**。

這讓同一張來源可在不同片段用於不同側，不必修改全域分類或重建時間軸。缺少來源、同張對比、時長／裁切錯誤等仍拒絕。ZIP仍為原版本1，沒有新增永久schema或複製照片。

## 刪除與復原資料流

- `frontend/photo-history.js` 保存最近一次刪除前／後的設定快照，圖片／標籤貼圖不進入序列化歷史。復原判斷優先使用既有正規化內容雜湊，避免Python欄位排序／預設值造成誤判；沒有版本context的測試或舊狀態使用排序後的設定比較。
- 所有刪除／提示／復原先操作前端草稿，不逐次呼叫Python。刪除時一起移除引用來源的片段，更新封面並沿用原有時間軸截短規則；取消提示不動內容。
- 下載／輸出的既有批次交易附帶最近刪除ID，Python完成所有資料驗證後，只保留最近一張已刪來源於工作階段 `photo_undo`。原照片工作副本bytes保留，縮圖只計算並快取一次。
- 同步後或同分頁元件重建後，復原使用這張來源的縮圖／雜湊；下一次既有批次交易附 `restore_photo` ID，後端只允許恢復自己保留的同ID來源，完整驗證成功後才交換。來源失效或驗證失敗保留現況，不假裝成功。
- 清空、登出、匯入取代仍走原資料保護；核准重設時清除復原來源。伺服器重啟不是永久復原，請使用ZIP備份。

## 數量與記憶體

- 活躍來源上限仍12張、80 MB／6000萬工作畫素，未提高上限。
- 本地刪除即移出時間軸；伺服器來源名額在下一次既有批次同步時釋放，例如直接下載ZIP／輸出MP4，無須先套用。若已滿12張且要立刻再上傳，仍可使用既有進階同步釋放名額；這是第三階段沿用的媒體庫同步限制。
- 復原會再檢查12張及工作階段容量，超限時拒絕，不自動縮小已編輯的來源。
- 歷史只有最近一次刪除；Python最多保留一張額外工作副本，正常載入的單張上限15 MB，另有最多約2 MB JPEG的預覽（Base64約2.7 MB），不無限制累積來源。既有背景輸出快照另依第三階段限量規則管理。
- 檔案替換沿用第二階段：同ID交換工作副本、保留設定，沒有把每次替換舊檔再加入復原堆疊。
- ZIP白名單只保存活躍照片及正式配對，不包含刪除歷史、建議、拒絕記錄、密碼或金鑰。

## 版本與成果

查看／拒絕建議、刪除影響提示、取消、選取及預覽不呼叫內容變更。接受、更換、交換、刪除及成功復原才更新正式草稿版本；沒有實際變更時沿用內容雜湊，不增加內容revision。

既有MP4仍保留。正式設定改變後顯示舊版，建議本身不讓MP4／ZIP過期。ZIP一鍵下載、MP4自動同步、固定快照、錯ACK保護、下載去重與備份A／草稿B的判斷都沿用第三階段。

## 真實瀏覽器驗證

使用loopback本機Streamlit、測試密碼、三張自行產生的紅／藍／綠圖片，在Codex內建瀏覽器完成：

1. 雙上傳區自動追加1張施工前、2張施工後，不按匯入；依檔名及分類產生1組低信心建議，沒有呼叫AI。
2. 接受後新增1組，交換前後後仍為5秒片段，設定顯示正確兩側。
3. 刪來源先提示實際影響1組配對；確認後剩2張來源、0組配對。
4. 不手動同步，點一次ZIP得到真實下載檔；以 `load_archive()` 讀入確認2張來源、0組配對，沒有刪除歷史。
5. ZIP同步完成後按復原，回到3張來源及原配對，ZIP正確標舊版；另外以進階同步測試確認復原來源能通過後端驗證，草稿回到已同步。進階操作只是驗收，不是一般下載／輸出的必要步驟。

瀏覽器工具的檔案選擇／下載觸發曾長時間回傳，但最終收到下載事件及檔案；不能以工具等待時間推論Cloud效能。自製純色圖只驗證流程，不代表真實室內照片配對準確率。

## 已知限制與人工驗收

- 僅最近一次來源刪除可復原；刪除後若有實際內容修改，為避免覆蓋新編輯會拒絕復原。這不是任意步驟Undo／Redo。
- 照片分類／既有AI描述通常不足以證明同一視角。請人工核對，不會新增AI分析補足資料；無建議仍可手動配對。
- 更換／交換保留文字內容，故文字若明確寫了某張照片特徵，需自行核對；AI定位標待確認，人工座標不自動覆蓋。
- Chrome、Edge、手機觸控與正式Streamlit Cloud尚未完成此次人工驗收。跨瀏覽器衝突勾選、長列表、更換不同長寬比、超限復原、背景MP4同時操作及接近ZIP上限仍建議實測。
- 部署後先備份，再依序測建議／拒絕、接受共用來源、更換／交換、刪除／取消／復原、直接ZIP往返與MP4，核對舊MP4保留及備份狀態。Cloud若因熱更新保留舊介面，先確認備份再Reboot；不宣稱Git推送即代表Cloud驗收成功。
